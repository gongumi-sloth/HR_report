# 하드스킬 추출 API 설계 (JD 구조화 워크플로우)

> 비정형 채용정보 → **표준 JD 구조화 + 하드스킬 추출** API의 개발 계약.
> 프리즘 BP · 2026-06-16 · 출처: JD 구조화 워크플로우 API 설계 초안(최고운, SRS r17 연계) + [[하드스킬-추출-플로우-20260615]]

---

## 1. 범위와 위치

- **이 API가 하는 일**: 고객사 비정형 채용정보 → ① 표준 JD(8섹션) 구조화 → ② **하드스킬 추출**(5범주 · capability 문장).
- **하지 않는 일(범위 밖)**: 자소서 **검출/검증**, 평가·점수화, 면접질문 생성. → 별도 워크플로우.
- **기존 5단계 흐름과의 매핑** ([[하드스킬-추출-플로우-20260615]]):

| 5단계 흐름 | 이 API |
|---|---|
| ① 접수 (JD 업로드) | `POST /v1/jd:structure` 입력 |
| ② 추출 (프롬프트①) | **이 API가 담당** — 단, flow 문서의 `{name, jd_evidence}`를 **5범주·capability 스키마로 확장** |
| ③ 확장(키워드) · ④ 검출(자소서) · ⑤ 표시 | 후속 API/단계 (이 문서 범위 밖) |

> 즉 이 API의 출력 `required_hard_skills[]`가 [③확장→④검출]을 거쳐 결과지 `hard_skills.항목[]`이 된다.

---

## 2. 엔드포인트

| Method · Path | 용도 | 비고 |
|---|---|---|
| `POST /v1/jd:structure` | 비정형 입력 → 구조화 JD + 하드스킬 추출 (draft 생성) | LLM 호출. 핵심 |
| `GET /v1/jd/{jd_id}` | 구조화 결과 조회 (3출력형식 선택) | `?format=doc\|json\|xlsx` |
| `PATCH /v1/jd/{jd_id}` | 운영(어드민) 검수 반영 → 확정 | `review_status: draft→confirmed` |
| `POST /v1/jd/{jd_id}:archive` | 확정본을 고객사·채용 키로 아카이빙(재사용) | flow 결정 2 |
| `GET /v1/jd/profiles?customer_id=&posting_id=` | 아카이빙 프로파일 조회·재사용 | — |

> 키워드 확장(③)·자소서 검출(④)은 별도 엔드포인트(`/v1/hard-skills:expand`, `:detect`) — 본 문서 범위 밖, 이름만 예약.

## 3. 요청 — `POST /v1/jd:structure`

```json
{
  "customer_id": "hanil",
  "posting_id": "2026-prod-newgrad",
  "source": {
    "raw_text": "<고객사가 준 비정형 텍스트 전체>",   // 둘 중 하나 이상
    "structured": {                                  // 이미 항목이 나뉘어 오면 사용
      "job_title": "생산기술 엔지니어",                  // [필수]
      "hiring_purpose": "결원 충원",                    // [권장]
      "key_responsibilities": ["...", "..."],          // [필수]
      "required_competencies": "공정 데이터 분석, SPC, …", // [필수]
      "team": null, "tools": null, "industry": null,
      "seniority": null, "nice_to_have": null,
      "performance_goals": null, "education_level": null
    }
  },
  "options": { "output_formats": ["json"], "locale": "ko" }
}
```

**필수 필드(누락 시 처리)** — 누락이면 `422` 미반환 항목은 `missing_information`에 적고 가능한 범위까지 진행:

| 필드 | 누락 시 |
|---|---|
| `job_title` | **중단** + `missing_information:["job_title"]` → 고객사 재요청 |
| `key_responsibilities` | **중단** + 고객사 재요청 |
| `required_competencies` | 진행 가능하나 `required_hard_skills` 비어 있을 수 있음 명시 |
| `hiring_purpose` | `missing_information` 표시 후 진행 |

**선택 필드**: `team · collaboration_targets · tools · industry · seniority · nice_to_have · performance_goals · education_level` — 누락 시 `"미입력"`(연차·학력 등 **임의 추정 금지**).

## 4. 응답 (200)

```json
{
  "jd_id": "jd_01H...",
  "review_status": "draft",
  "structured_jd": {
    "team": "미입력",
    "jd_title": "생산기술 엔지니어",
    "application_qualifications": "…",
    "job_purpose": "…",
    "key_responsibilities": ["…"],
    "performance_kpi": ["…"],
    "required_hard_skills": [ /* §5 스키마 */ ],
    "nice_to_have_requirements": ["…"]
  },
  "required_hard_skills": [
    {
      "id": "hs_1",
      "category": "method_based",
      "name": "SPC(통계적 공정관리)",
      "rewritten_as_capability": "관리도로 공정 변동을 모니터링하고 이상 패턴을 식별해 개선안을 제시할 수 있음.",
      "evidence_from_input": "공정 변동 분석 및 품질관리",
      "source_field": "required_competencies",
      "requirement_type": "must_have"
    }
  ],
  "meta": {
    "missing_information": ["hiring_purpose"],
    "ambiguity_flags": [
      { "field": "seniority", "note": "‘신입/경력 무관’으로 해석 — BU 확인 필요" }
    ],
    "extraction_notes": "‘데이터 분석’은 method_based로 분류(도구 미명시).",
    "quality_gate": { "passed": true, "failed_items": [] }
  }
}
```

### 핵심 출력 = `required_hard_skills[]` (BP 파이프라인 소비처)
| 필드 | 규칙 |
|---|---|
| `category` | `tool_based \| method_based \| knowledge_based \| experience_based \| output_based` (§5-1) — **enum 고정** |
| `name` | 하드스킬 식별명 (짧게) |
| `rewritten_as_capability` | **"무엇을 할 수 있어야 하는가"** = 목적어+동사+관찰 가능 결과물 (§5-2) |
| `evidence_from_input` | 입력 원문 일부 **그대로 보존** (무근거 금지) |
| `source_field` | 추출 출처 필드 (`required_competencies` 등) |
| `requirement_type` | `must_have \| nice_to_have` — 평가 가중치 입력용 |

## 5. 하드스킬 추출 규칙 (서버/LLM 적용)

### 5-1. 5범주 (한 항목이 겹치면 가장 강한 범주 우선, 근거는 `extraction_notes`)
| category | 정의 | 예 |
|---|---|---|
| `tool_based` | 도구·시스템·SW 사용 | Tableau, SAP, AWS S3 |
| `method_based` | 방법론·분석 방식·절차 | A/B 테스트, 회귀분석, SPC |
| `knowledge_based` | 이론·규정·도메인·전공 지식 | 통계학, GAAP, 공정 화학 |
| `experience_based` | 수행·프로젝트·산업·연구 경험 | "ESS 5MWh 설치 1건↑" |
| `output_based` | 산출물·보고서·결과물 생성 | "월별 KPI 리포트 작성" |

### 5-2. capability 변환
- 단순 키워드 금지 → `rewritten_as_capability`에 **목적어(대상)+동사+관찰 가능한 결과물** 한 문장.
- 예: `Excel` → "스프레드시트로 데이터를 정리하고 조건별 필터링·기본 통계 요약을 수행할 수 있음."

### 5-3. 무근거 금지 (hallucination 차단)
- 명시된 내용만 확정 → `evidence_from_input`에 원문 보존. AI 해석은 `ambiguity_flags`로 분리.
- **임의 추가 절대 금지**: 미제공 팀명·부서명·경력연차·학력·보상·근무지·고용형태.
- Hard skill ↔ Soft skill 혼동 금지(품질게이트 hard fail, §9).

---

## 6. 처리 흐름 (서버 내부)

```text
1) 입력 정규화: source.raw_text → 필수/선택 필드 매핑 (structured 우선)
2) 필수 검증: job_title·key_responsibilities 누락 → 422 (+ missing_information)
3) LLM 추출(프롬프트 §7): structured_jd + required_hard_skills(draft) + meta
4) 품질 게이트 6항 자동검사(§9): hard fail이면 재실행 or 플래그
5) draft 저장(review_status=draft) → 운영 검수(PATCH) → confirmed
6) 확정본 아카이빙(고객사·채용 키) → 재사용 조회 가능
```

---

## 7. LLM 프롬프트 계약 (프롬프트① 확장판)

추출은 **정규식/파서가 아니라 LLM 프롬프트**로 한다(의미 분류·capability 재작성·soft skill 배제·동음이의 판단이 필요). 기존 flow의 프롬프트①(`{name, jd_evidence}`)을 **5범주·capability·메타 스키마로 확장**한다.

### 7-1. 시스템/지시 프롬프트 (실 사용 텍스트)
```text
너는 채용 직무기술서(JD)에서 '하드스킬(hard skill)'을 추출·구조화하는 전문가다.
입력 JD에서 평가 가능한 하드스킬만 뽑아 지정된 JSON으로만 출력한다.

[하드스킬 정의]
- 하드스킬 = 학습·훈련으로 습득되어 객관적으로 확인 가능한 직무 수행 능력(도구·방법론·지식·경험·산출물).
- 소프트스킬(협업·커뮤니케이션·책임감·적극성·열정 등 태도·성향)은 추출하지 않는다.

[5개 카테고리] (한 항목이 여러 범주에 걸치면 가장 강한 범주 하나로 분류, 근거는 extraction_notes에)
- tool_based      : 특정 도구·시스템·SW 사용 (Tableau, SAP, AWS S3)
- method_based    : 방법론·분석 방식·절차 (A/B 테스트, 회귀분석, SPC)
- knowledge_based : 이론·규정·도메인·전공 지식 (통계학, GAAP, 공정 화학)
- experience_based: 수행·프로젝트·산업·연구 경험 ("ESS 5MWh 설치 1건 이상")
- output_based    : 산출물·보고서·결과물 생성 ("월별 KPI 리포트 작성")

[capability 변환 — rewritten_as_capability]
- 단순 키워드 금지. "무엇을 할 수 있어야 하는가"로 변환한다.
- 한 문장에 반드시 [목적어(대상) + 동사 + 관찰 가능한 결과물]이 들어간다.
- 예: "Excel" → "스프레드시트로 데이터를 정리하고 조건별 필터링·기본 통계 요약을 수행할 수 있음."

[무근거 금지 규칙]
- JD에 명시된 내용만 확정 추출한다. 각 항목은 입력 원문 일부를 evidence_from_input에 그대로 보존한다.
- 추론·해석으로 보충한 내용은 ambiguity_flags로 분리한다(확정 항목에 섞지 않는다).
- JD에 없는 팀명·부서명·경력연차·학력·보상·근무지·고용형태를 절대 임의로 추가하지 않는다.
- 하드스킬을 구성할 수 없을 만큼 모호하거나 누락된 정보는 missing_information에 적는다.

[필수/우대 구분]
- 지원자격·필수요건 → requirement_type="must_have", 우대사항 → "nice_to_have".

[출력] 아래 JSON만 출력한다(설명 문장·코드펜스 없이):
{
  "required_hard_skills": [
    { "category": "<5범주 중 하나>", "name": "<짧은 식별명>",
      "rewritten_as_capability": "<목적어+동사+결과물 한 문장>",
      "evidence_from_input": "<JD 원문 일부 그대로>",
      "source_field": "<key_responsibilities|required_competencies|nice_to_have>",
      "requirement_type": "must_have|nice_to_have" }
  ],
  "missing_information": ["<JD 구성 불가 누락 항목>"],
  "ambiguity_flags": [ { "field": "<필드>", "note": "<해석/추정 근거>" } ],
  "extraction_notes": "<적용 규칙·범주 결정 근거 메모>"
}

[입력 JD]
{{structured_jd_input}}
```

### 7-2. few-shot 예시 (앵커용 1건)
- 입력 `required_competencies`: "SQL과 BI 도구로 마케팅 지표를 집계·시각화. 디지털 광고 3종 이상 운영 경험. 협업 능력 우수."
- 출력:
```json
{
  "required_hard_skills": [
    { "category": "tool_based", "name": "SQL·BI 도구",
      "rewritten_as_capability": "SQL과 BI 도구로 마케팅 지표를 집계하고 채널별 성과를 시각화해 보고할 수 있음.",
      "evidence_from_input": "SQL과 BI 도구로 마케팅 지표를 집계·시각화",
      "source_field": "required_competencies", "requirement_type": "must_have" },
    { "category": "experience_based", "name": "디지털 광고 채널 운영 경험",
      "rewritten_as_capability": "디지털 광고 채널 3종 이상에서 캠페인 기획·집행·분석을 수행한 경험이 있음.",
      "evidence_from_input": "디지털 광고 3종 이상 운영 경험",
      "source_field": "required_competencies", "requirement_type": "must_have" }
  ],
  "missing_information": [],
  "ambiguity_flags": [],
  "extraction_notes": "‘협업 능력 우수’는 soft skill이라 추출 제외."
}
```
> 입력은 §3 구조화 JD(또는 raw_text 정규화 후). 모델·토큰·게이트웨이는 [[하드스킬-추출-플로우-20260615]] '연동 항목'에서 확정. 출력은 §9 품질 게이트 통과 후 운영 검수(draft→confirmed).
> ※ 이 프롬프트는 **추출**용. 자소서에서의 **검출/미검출 판단**은 별도 프롬프트(flow 문서 프롬프트③ — 검출).

## 8. 상태 코드

| 코드 | 상황 |
|---|---|
| `200` | 구조화 성공 (draft) — 일부 `missing_information` 있어도 200 |
| `422` | 필수(`job_title`/`key_responsibilities`) 누락 → 진행 불가 |
| `409` | 동일 customer_id·posting_id draft 중복 (override 옵션 필요) |
| `200` (PATCH) | 검수 반영·확정 |

## 9. 품질 게이트 (검수 전 자동검증, `meta.quality_gate`)

| # | 항목 | 실패 처리 |
|---|---|---|
| 1 | 원문 핵심 단어가 `evidence_from_input`에 보존 | 누락 → 재실행 |
| 2 | Hard ↔ Soft 미혼동 | **hard fail** → 재분류 필수 |
| 3 | 각 항목 행동 가능 문장(capability)화 | 키워드만 → `rewritten_as_capability` 보강 |
| 4 | 지식 ↔ 경험 분리 | 한 항목에 섞이면 분리 |
| 5 | 추정 ↔ 확정 구분(`evidence_from_input` 빈데 flag 없음 = 환각 위험) | flag/제거 |
| 6 | 추가확인 항목 표시(`missing_information`) | 완전 입력이면 "완전" 명시 |

## 11. 결과지(4.2) 연결 + 현재 상태

- `required_hard_skills[]` → [③ 키워드 확장 → ④ 자소서 검출] → 결과지 `hard_skills.항목[]`(`{name, status:검출\|미검출, summary, evidence_ids[]}`).
- 즉 이 API는 결과지 하드스킬의 **"스킬 목록(추출)"** 원천이고, **검출/미검출은 후속 검출 API** 소산.
- **현재**: 한일시멘트 생산직 **JD 미수령** → 본 문서는 **API 설계만**. 실데이터 추출·결과지 반영은 JD 수령 후. (현 결과지 `hard_skills`는 INTERIM 수작업 — 작업계획서 §11-2)

## 결정 필요 (개발 착수 전)

- **동기/비동기**: LLM 지연 → v1 동기(타임아웃) vs job 큐(비동기 polling). *(기본 제안: v1 동기)*
