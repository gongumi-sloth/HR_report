## 1. 개요
- 한 지원자의 BP 평가 결과(factor 등급·근거요약·총점)를 근거로 **한 문장**(강점 + 단점 + 채용 액션, 두괄식)을 생성하는 LLM API. **본 API 범위는 `one_liner` 출력까지**이며, 결과지 노출 위치는 소비측이 결정.
- 구현: 공통 **execute API** + **공방 프롬프트**(입력변수 `{{ }}` + 출력 JSON Schema).
- execute API 사용 조건 충족: ① 응답을 후처리 없이 그대로 사용 ② 출력 schema 고정.
- **강점·단점은 실측 출력(점수·등급·근거)에서 도출**하고, **액션만 새로 생성**한다(새 사실 생성 아님 = 합성).
- (범위 외) GPK(AI 작성 탐지)는 한 줄 코멘트에 **반영하지 않음**(의도).

## 2. Service URL
- 공통 execute: `{protocol}://{IP_or_domain}/common/prompt-execute/` — 실제 엔드포인트는 Q4.
- 본 API는 위 엔드포인트를 `workspaceName` + `promptName`으로 호출해 지정 프롬프트를 실행한다.

## 3. 워크플로우
```
[EVALUATE-CUSTOM-FACTOR] (수정 안 함) — 전체 factor 채점: grade·explain·score
[BP 점수 산출 API]        총점(total_score) · 직군 내 상위%
        │
        ▼  [선별] 등급 상위 2(강점)·하위 2(검토) + tie-break  ← 결정적 코드, 1회·공유(§3-1·§3-2)
   4 factor (강점2·검토2) + standing
        ▼  digest 구성(§4-1)
[execute API]  공방 프롬프트(workspaceName+promptName) 실행(LLM) → 출력 JSON Schema(Strict)
result { one_liner, char_count, parts, meta }
        ▼
결과지 노출 (위치는 소비측 결정) · 같은 4 factor를 검증포인트 섹션도 공유
```

## 3-1. 강점/검토 factor 선별 규칙 (호출 전 단계 — LLM 아님)

> **선별 주체:** LLM이 아니라 **호출측 코드(또는 업스트림)** 가 결정적으로 처리하고, 본 API에는 선별 결과만 넘긴다. 구현 위치는 개발팀 판단(§3-2).

- **강점 = factor 등급 상위 2개**, **검토 = 등급 하위 2개** (factor는 항상 ≥4개).
- 강점이 반드시 `high`는 아니다(상위 2개일 뿐 `mid`일 수 있음). 프롬프트는 실제 `grade`·`evidence_summary`에 맞게 서술.

**등급 동점 시 우선순위** (위 = 우선)
1. 직무역량의 역량분자 → 2. 직무경험 → 3. 직무지식 → 4. 직무동기(직무적합도) → 5. 조직적합도의 역량분자 → 6. 직무동기(지원동기) → 7. 회사동기 → 8. 답변적합도 → 9. 구체성 → 10. 본인소개

> 검토 동률·롤업(같은 메트릭 `none` 클러스터를 상위 메트릭 1개로 묶음)은 §3-2 참조.

## 3-2. 개발 요청 — 선별 단계 구현

> 개발자 전달용. EVALUATE-CUSTOM-FACTOR가 반환한 **전체 factor**(등급·score 포함) 위에서 도는 **작은 선별 단계**를 추가해 주세요. (EVALUATE 자체는 수정하지 말고 전체 반환 유지 — 결과지 상세 페이지가 전체를 씁니다.)
>
> **동작(결정적, LLM 불필요):**
> 1. 모든 factor를 등급순(high > mid > low > none) 정렬, 동률이면 §3-1 tie-break 우선순위 적용
> 2. **상위 2개 = 강점, 하위 2개 = 검토** (강점은 개별 유지 — 롤업 안 함). 단, **검토에서 같은 상위 메트릭의 `none` factor가 2개 이상이면 그 메트릭을 '평가 근거 없음'(level=metric) 1개로 롤업**
> 3. 이 4개(factor·등급·근거)를 한 줄 코멘트 execute 호출 입력(digest §4-1)으로 전달
>
> 이 선별 결과는 **결과지 검증포인트(강점/검토) 섹션도 동일하게 사용**하므로, **한 곳에서 계산해 양쪽이 같은 값을 참조**하게 해주세요(중복·불일치 방지). 구현 위치(호출측 inline / 공용 함수 / 1회 계산 후 저장)는 개발팀이 자유롭게 정하셔도 됩니다.
>
> ※ factor ↔ 상위 메트릭 grouping은 EVALUATE-CUSTOM-FACTOR 출력의 metric 구조를 그대로 따른다(별도 매핑 불필요).

### 4-1. keyValue.evaluation_digest 구조 (입력 digest)
```json
{
  "candidate_ref": "0001",
  "position": "생산팀(화공)",
  "factors": [
    { "role": "strength", "rank": 1, "level": "factor", "name": "직무 경험", "grade": "high", "evidence_summary": "석사 과정 폴리이미드 연구로 접착 강도 30배 향상, Scale-up 공정 최적화를 직접 경험." },
    { "role": "strength", "rank": 2, "level": "factor", "name": "직무 지식", "grade": "high", "evidence_summary": "공정 화학·고분자 전공 지식을 생산 공정 개선에 적용한 사례 제시." },
    { "role": "review",   "rank": 1, "level": "metric", "name": "조직적합도", "grade": "none", "evidence_summary": "조직적합도(리더십·협업 등) 전반에 대한 평가 근거를 찾을 수 없음." }
  ],
  "standing": {
    "total_score": 63.26,
    "percentile_top": 50
  }
}
```
| 필드 | 설명 · 출처 |
|---|---|
| `factors` | **강점 2개 + 검토 1~2개**. 선별=등급 상위 2(강점)/하위 2(검토)+tie-break, **같은 메트릭 none 클러스터는 메트릭 롤업**(§3-2). 각 항목: `level`(`factor`\|`metric`)·`name`(역량명 또는 메트릭명)·`grade`·`evidence_summary`(Q7)·`rank`(선별 순위 — 정렬용 메타, LLM 미사용). 위 예는 롤업(검토 1개); 일반 케이스는 검토가 `level=factor` 2개. 출처 = EVALUATE `result[].factor`/`grade`/`explain` |
| `standing` | `total_score`(총점) + `percentile_top`(**직군 내 상위 %**). **'다음 액션'의 어조·강도 판단용 — 수치는 문장에 단정 출력하지 않음**(합불 입력 없음) |

## 5. 프롬프트

### 5-1. 입력 변수
- `{{evaluation_digest}}` — §4-1 digest JSON
- `{{max_chars}}` — 한 문장 최대 글자수. keyValue엔 **문자열**로 전달(예 `"90"`)

### 5-2. 시스템/지시 프롬프트 (실 사용 텍스트)
```text
너는 채용담당자를 위해 BP 평가 결과를 '한 문장'으로 요약하는 전문가다.
아래 [평가 데이터](강점·검토 factor의 등급·근거요약, 종합 standing)만 근거로, 지정된 JSON 스키마로만 출력한다.

[입력 구조]
- position: 지원 직무(코멘트의 직무 맥락으로 활용).
- factors: 강점 2개(등급 상위 2개) + 검토 1~2개(등급 하위). 각 항목에 level(factor|metric)·name(역량명/메트릭명)·grade·evidence_summary. **level=metric이면 그 상위 메트릭 전반의 근거가 없는 경우**(같은 메트릭 none 다수 롤업). 강점이라도 반드시 'high'는 아니다.
- standing: total_score(총점), percentile_top(직군 내 상위 %).

[문장 구성 — 한 문장에 3요소 모두]
1) 강점: role="strength" 항목 1~2개를 grade·근거요약(evidence_summary)에 맞게 **position(직무) 맥락에서** 직무 중심으로 통합한다. (grade가 high면 단정적 강점, mid 이하면 '상대적으로 두드러진' 식으로 완화)
2) 단점: role="review" 항목을 근거로 표현한다. level=metric이면 "(메트릭명) 전반의 근거가 확인되지 않음"으로, level=factor이면 그 역량이 "확인되지 않음 / 근거 부족"으로.
3) 액션: 단점과 직접 연결된 '면접에서 확인할 점' 1개를 제시한다.

[순서] 두괄식 — 강점을 문장 맨 앞에 둔다. (강점 → 단점 → 액션)

[액션의 어조·강도]
- 액션의 '내용'은 검토 항목에서 정한다. '어조·강도'는 standing(percentile_top·total_score)으로 적극/신중을 가늠한다(합불 신호 없음).
- ※ standing 수치(상위 %·총점)는 어조 판단에만 쓰고, one_liner 문장에 숫자로 단정해 넣지 않는다.
- '합격/불합격/적격/부적격/탈락'을 직접 쓰지 않는다(법령). '권장/검토 필요/확인'으로 표현한다.
- 지원자를 단정·비하하지 않는다.

[무근거 금지]
- 입력 factors(근거요약)·standing에 있는 내용만 쓴다. 근거요약이 비었거나 grade가 낮은 강점은 단정하지 말고 상대적으로 표현한다(없는 근거 생성 금지).
- 상위 %·배수 컷 등은 문장에 수치로 단정해 넣지 않는다.

[길이] 한 문장, {{max_chars}}자 이내. 초과하면 비교수치 → 수식어 순으로 줄인다.

[자연스러움 검토 — 출력 직전 필수]
- one_liner가 자연스러운 한국어 한 문장인지 스스로 검토하고, 어색하면 의미를 유지한 채 다듬어 출력한다.
  (번역투·어색한 조사/어미·중복·비문 없이, 강점 → 단점 → 액션이 매끄럽게 이어질 것)

[출력] 지정한 JSON 스키마로만 출력한다(설명·코드펜스 없이):
- one_liner : 한 문장(결과지 노출 대상)
- char_count : one_liner의 글자 수(공백·문장부호 포함)
- parts.strength / parts.weakness / parts.action : 강·약·액션 분해
- meta.grounded : 입력에 없는 영역/등급을 쓰지 않았으면 true
- meta.used : 사용한 근거 목록(예: "직무 경험:high", "리더십 역량:none")
- meta.notes : 짧은 메모

[평가 데이터]
{{evaluation_digest}}
```
프롬프트 공방 ID : (추가 예정)

### 5-3. 출력 JSON Schema (공방 Output Schema · Response Type=JSON Schema · Strict Mode)
```json
{
  "type": "object",
  "required": ["one_liner", "char_count", "parts", "meta"],
  "properties": {
    "one_liner": { "type": "string" },
    "char_count": { "type": "integer" },
    "parts": {
      "type": "object",
      "required": ["strength", "weakness", "action"],
      "properties": {
        "strength": { "type": "string" },
        "weakness": { "type": "string" },
        "action": { "type": "string" }
      },
      "additionalProperties": false
    },
    "meta": {
      "type": "object",
      "required": ["grounded", "used", "notes"],
      "properties": {
        "grounded": { "type": "boolean" },
        "used": { "type": "array", "items": { "type": "string" } },
        "notes": { "type": "string" }
      },
      "additionalProperties": false
    }
  },
  "additionalProperties": false
}
```
> Strict Mode 규칙상 `properties`의 모든 키는 `required`에 포함(선택 필드 없음). `char_count` = one_liner 글자 수(다른 기능에서 활용). ※ **LLM 자체 계산이라 부정확할 수 있음**(execute API는 후처리 없음) — 정확한 값이 필요한 기능은 `one_liner`로 **재계산** 권장.

## 7. 품질 가드레일
1. 강·약·액션 3요소 포함 — 누락 시 재생성
2. 금지어(합격/불합격/적격/부적격/탈락) 미사용 — **hard fail**
3. `grounded=true`(입력에 없는 영역/등급 미등장, `none` 역량을 강점으로 쓰지 않음) — **hard fail**
4. 길이 ≤ `max_chars` — 초과 시 압축
5. 두괄식(강점 선두) · 어조는 standing 기준 정합(§5-2)
6. 자연스러운 한국어 한 문장 — 어색하면 의미 유지한 채 다듬어 재출력

> execute API는 후처리를 하지 않으므로 위 게이트는 **프롬프트에 내장**한다. 하드-페일 자동 재생성을 *프로그램적으로* 강제해야 하면, 호출측에 얇은 재시도 래퍼를 후속 추가.
