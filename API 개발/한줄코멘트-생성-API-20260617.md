# 한 줄 코멘트 생성 API 기획 (메모)

> 한 지원자의 BP 평가 결과를 **한 문장**(강점 + 단점 + 채용 액션)으로 요약해 결과지 최상단(두괄식)에 보여주는 LLM API.
> 프리즘 BP · 2026-06-17 · 출처: 한일시멘트 파이프라인(`한일시멘트/작업계획서.md` §11·§13) + 기획 의도

---

## 0. 배경 — 무엇이 "있는 데이터"인가 (먼저 짚기)

- 한일시멘트 결과지(목업)는 그 안에서 완결되지만 **실제 제품으로 구현된 것은 아니다.**
- 그래서 한 줄 코멘트는 **"현재 개발돼 있는 BP API가 실제로 내보내는 출력"만 입력으로 쓸 수 있다.** 목업 데이터셋(`dataset-응시자N.json`)의 `verification`(강점/검토 코멘트·**면접질문**)·`summary.headline`·`evaluation.항목[].summary`(상세 코멘트)는 **우리가 생성한 더미**다(작업계획서 §11-2 "API에 값은 있으나 미접근 → 임의 생성"). → **이 코멘트의 입력으로 가정하면 안 된다.**
- 결론: 한 줄 코멘트 API는 그 자체로 **§13-3의 "코멘트 자동생성(C)" 단계**다. 강점·단점은 실제 출력인 **점수·등급·근거**에서 *도출*하고, **액션은 새로 생성**한다.

---

## 1. 입력 데이터 = 현재 BP API의 실제 출력

> 실물 기준: prism 서버렌더 결과지 추출물 `한일시멘트/data/extracted/applicantN.json`. 아래가 **실제로 존재하는** 필드다.

| 쓸 수 있는 것 (실측 출력) | 실제 필드 | 코멘트에서의 쓰임 |
|---|---|---|
| 총점 | `top_score` | 어조 판단 보조 |
| 6메트릭 점수·반영비율 | `item_scores[]` / `chart.metricWeight[]` | 강·약 영역 판별 |
| **전형 평균** | `chart.metricAverage[]` | 평균 대비 강/약 |
| **역량 등급** | `metrics[].factors[].grade` = `high\|mid\|low\|none` | **강점=high / 단점=none·low** |
| 근거문장(번호·원문) | `metrics[].factors[].sent[]` + `questions[].evidence[]` | 강점 문구의 **사실 근거**(인용) |
| GPK 탐지여부 | `gpk.q1·q2` (`탐지/미탐지`) | (선택) 신뢰성 단서 |

**쓸 수 없는 것 (실제 출력 아님 — 가정 금지)**
- 강점/검토 선별 코멘트, **면접질문**, 상세평가 코멘트 → 전부 생성 더미. **이 API가 대신 만들어야 할 대상**이지 입력이 아니다.
- 상위 %(`percentile`)·배수 컷(`cut`)·상위10%(`top10`) → 현재 **5명 소표본 가정값**(작업계획서 §13-2). 신뢰성 낮음 → 코멘트 본문에 수치로 단정 노출 지양.

> ⚠️ **실제 API의 HTTP 응답 스키마/접근 방식은 개발팀이 확정**한다. 위 표는 "의미상 무엇이 있는가"이며, 한일시멘트에선 prism URL 추출로 얻었다. 정식 API 필드명·엔드포인트는 §6 확정 필요.

## 2. 데이터 흐름

```
[현재 개발된 BP API 출력]
   점수 7종 · 역량 등급(high/mid/low/none) · 근거문장 · 전형평균 · GPK
   (한일시멘트 파이프라인 = 엑셀 + prism URL 추출 → data/extracted/applicantN.json)
        │
        ▼   ← digest 추출(§3 입력 스키마로 정규화)
[한 줄 코멘트 생성 API]  POST /v1/bp/one-liner   (LLM)
   강점 = 높은 등급/평균상회 영역  ·  단점 = none·low/평균하회 영역  ·  액션 = 면접 확인 생성
        │
        ▼
   one_liner 한 문장  →  결과지 최상단 렌더
   (한일시멘트: dataset 신규 필드 → build_reports.py 토큰 {{ONE_LINER}} → P1 최상단)
```

- **위치**: gen_datasets의 생성 코멘트군과 동일 계열 → 같은 단계에서 호출. 현재는 INTERIM 수작업, API 구현 시 교체(§13-2의 C 항목).
- **재료가 이미 다 있음**: 점수·등급·근거는 실측이라, 코멘트는 *합성*만 하면 된다(새 사실 생성 아님).

## 3. 입력 스키마 (digest) · 출력

### 요청 — `POST /v1/bp/one-liner`
```json
{
  "candidate_ref": "0001",
  "position": "생산팀(화공)",
  "total_score": 63.26,
  "metrics": [
    { "code": "JOB", "label": "직무적합도", "score": 73.87, "average": 71.53, "weight": 25 },
    { "code": "ORG", "label": "조직적합도", "score":  5.60, "average": 29.72, "weight": 20 },
    { "code": "MOT", "label": "지원동기",  "score": 70.43, "average": 61.17, "weight": 20 },
    { "code": "QNA", "label": "답변적합도", "score": 77.14, "average": 79.41, "weight": 10 },
    { "code": "SPC", "label": "구체성",    "score": 87.39, "average": 75.54, "weight": 20 },
    { "code": "EGO", "label": "본인소개",  "score": 88.07, "average": 79.10, "weight":  5 }
  ],
  "factors": [
    { "area": "직무적합도", "name": "직무 경험", "grade": "high", "evidence_no": ["1","3","9"] },
    { "area": "조직적합도", "name": "리더십 역량", "grade": "none", "evidence_no": [] },
    { "area": "조직적합도", "name": "팀워크 역량", "grade": "mid",  "evidence_no": ["5","13"] }
  ],
  "evidence": { "1": "석사 과정에서 폴리이미드…접착 강도를 30배 향상…", "9": "…Scale-up 공정 최적화를 직접 경험…" },
  "gpk": { "detected": true },
  "pass": { "label": "3배수 이내", "positive": true },
  "options": { "max_chars": 90, "locale": "ko" }
}
```
> `pass`는 **접수 단계에서 합불 기준을 선택한 경우만**. 없으면 어조는 평균/총점 기준으로 판단(§4).

### 응답 (200)
```json
{
  "one_liner": "직무 경험·지식이 평균을 웃돌 만큼 탄탄하지만, 조직 적합 역량(리더십·협업)이 거의 확인되지 않아 면접에서 조직 적응·협업 경험 확인을 권장합니다.",
  "parts": {
    "strength": "직무 경험·지식 (평균 상회)",
    "weakness": "조직 적합 역량 미확인 (조직적합도 5.6 / 평균 29.7)",
    "action":   "면접에서 조직 적응·협업 경험 확인 권장"
  },
  "tone": "recommend",
  "char_count": 83,
  "meta": { "grounded": true, "used": ["직무 경험:high","직무 지식:high","리더십 역량:none","ORG<avg"], "notes": "강점=high 2개·단점=none 몰린 영역·액션 1개" }
}
```

| 필드 | 규칙 |
|---|---|
| `one_liner` | 결과지 렌더 대상. 한 문장 · `max_chars` 이내 |
| `parts` | 강·약·액션 분해 — QA·구조 렌더용 |
| `tone` | `recommend`(pass.positive=true) \| `review`(false) — 액션 어조와 연동 |
| `char_count` | `one_liner`의 글자 수(**공백·문장부호 포함, `max_chars`와 동일 기준**). 길이 게이트(§6-4) 검증용 |
| `meta.grounded`/`used` | 무근거 검증: 입력에 없는 영역/등급 등장 시 false |

## 4. 생성 로직 (실제 출력에서 강·약·액션 도출)

- **강점**: `grade=="high"` factor 1~2개 (없으면 `score − average`가 가장 큰 메트릭). 근거문장(`evidence`)으로 사실 확인 후 직무 중심 1구로 통합.
- **단점**: `grade` `none`/`low`가 몰린 영역, 또는 `score < average`·절대값 낮은(특히 <40) 메트릭 1개. 우수자도 **상대적 최약 1개는 포함**(건설적).
- **액션**: 단점 영역을 **면접에서 확인**하는 1구를 *생성*(예: "조직 적응·협업 경험 확인"). ← 면접질문이 API에 없으므로 여기서 만든다.
- **어조**: `pass.positive` 있으면 그대로(true→"권장"/false→"검토 필요"). 없으면 총점·평균 기준(평균 이상→권장 톤, 미만→검토 톤).
- **순서(두괄식)**: 강점 → 단점 → 액션, 강점을 문장 맨 앞.
- **길이**: 한 문장 · `max_chars`(기본 90). 초과 시 비교수치 → 수식어 순 삭제.
- **법령**: `합격/불합격/적격/부적격/탈락` 금지 → `권장/검토 필요/확인`(AI기본법, SDS r25, 작업계획서 §9-5-①과 동일).
- **무근거 금지**: `factors`/`metrics`/`evidence`에 있는 것만. 등급이 `none`인 역량을 강점으로 쓰지 않는다. 상위% 등 소표본 가정값은 수치 단정 금지.

## 5. LLM 프롬프트 계약

### 5-1. 시스템/지시 프롬프트 (실 사용 텍스트)
```text
너는 채용담당자를 위해 BP 평가 결과를 '한 문장'으로 요약하는 전문가다.
아래 평가 데이터(점수·역량 등급·근거문장)만 근거로, 지정된 JSON으로만 출력한다.

[문장 구성 — 한 문장에 3요소 모두]
1) 강점: grade가 'high'인 역량 1~2개(없으면 score가 average보다 가장 높은 메트릭)를 직무 중심으로 통합
2) 단점: grade가 'none'/'low'가 몰린 영역 또는 점수가 평균보다 낮은(특히 40 미만) 메트릭 1개
         (강점이 뚜렷한 지원자도 상대적으로 가장 약한 영역 1개는 반드시 포함)
3) 액션: 단점과 직접 연결된 '면접에서 확인할 점' 1개를 제시

[순서] 두괄식 — 강점을 문장 맨 앞에 둔다. (강점 → 단점 → 액션)

[어조]
- pass.positive=true → 액션을 "...을 권장합니다"로, false → "...에 대한 검토가 필요합니다"로 맺는다.
  (pass 없으면 총점이 평균 이상이면 권장 톤, 미만이면 검토 톤)
- '합격/불합격/적격/부적격/탈락'을 직접 쓰지 않는다(법령). '권장/검토 필요/확인'으로 표현한다.
- 단점은 "근거 부족 / 확인되지 않음 / 확인 필요"로 표현하고, 지원자를 단정·비하하지 않는다.

[무근거 금지]
- 입력 factors·metrics·evidence에 있는 내용만 쓴다. grade가 'none'인 역량을 강점으로 말하지 않는다.
- 상위 %·배수 컷 등은 신뢰도가 낮으므로 문장에 수치로 단정해 넣지 않는다.

[길이] 한 문장, max_chars 이내. 초과하면 비교수치 → 수식어 순으로 줄인다.

[자연스러움 검토 — 출력 직전 필수]
- 확정한 one_liner가 '자연스러운 한국어 문장'인지 스스로 검토하고, 어색하면 의미를 유지한 채 다듬은 뒤 출력한다.
- 점검: 번역투·어색한 조사/어미·중복 표현·비문이 없는가 / 강점 → 단점 → 액션이 한 문장으로 매끄럽게 이어지는가 / 소리 내어 읽었을 때 한 번에 이해되는가.

[출력] 아래 JSON만 출력한다(설명·코드펜스 없이):
{
  "one_liner": "<한 문장>",
  "parts": { "strength": "<강점구>", "weakness": "<단점구>", "action": "<액션구>" },
  "tone": "recommend|review",
  "meta": { "grounded": true, "used": ["<쓴 근거: 역량:등급 / 메트릭 비교>"], "notes": "<메모>" }
}

[평가 데이터]
{{evaluation_digest}}
```

### 5-2. few-shot (앵커 1건 — 응시자1 실측)
입력 요지: 직무적합도 73.87(평균 71.53, 직무경험·직무지식 `high`) / 조직적합도 5.60(평균 29.72, 리더십·협상·갈등관리·의사소통·대인관계 `none`) / 구체성 87.39·본인소개 88.07 / pass "3배수 이내"(positive).

```json
  "parts": { "strength": "직무 경험·지식 (평균 상회)",
             "weakness": "조직 적합 역량 미확인 (조직적합도 5.6 / 평균 29.7)",
             "action": "면접에서 조직 적응·협업 경험 확인 권장" },
  "tone": "recommend",
  "meta": { "grounded": true, "used": ["직무 경험:high","직무 지식:high","리더십 역량:none","ORG<avg"], "notes": "강점 high 2개·단점 none 몰린 조직·액션 1개" }

```

## 6. 품질 게이트 + 결과지 연결

**게이트(생성 후 자동검증)**
1. 강·약·액션 3요소 포함 — 누락 시 재생성
2. 금지어(합격/불합격/적격/부적격/탈락) 미사용 — **hard fail**
3. `grounded=true` (입력에 없는 영역/등급 미등장, `none` 역량을 강점으로 쓰지 않음) — **hard fail**
4. 길이 ≤ `max_chars` — 초과 시 압축
5. 두괄식(강점 선두) · `pass` ↔ 어조 정합
6. **자연스러운 한국어 문장**(번역투·중복·비문 없이 한 문장으로 매끄럽게 읽힘) — 어색하면 의미 유지한 채 다듬어 재출력

**결과지 연결**: 출력 `one_liner` → dataset 신규 필드 → `build_reports.py` 토큰 → P1 **최상단** 렌더(두괄식). 디자인은 CLAUDE.md 토큰 준수.

## 결정·확정 필요 (개발 착수 전)

- **실제 BP API 인터페이스(가장 중요)**: §1 필드의 정식 응답 스키마·엔드포인트·접근 방식 = **개발팀 확정**. (한일시멘트는 prism URL 추출로 우회 — 정식 API 호출로 대체할지 포함.) → 내가 임의로 지어내지 않음.
- **호출 위치**: 별도 API 호출 vs 평가 산출 파이프라인 내 1스텝. *(제안: 평가 결과 생성 직후 1스텝, 동기)*
- **배치·디자인**: 두괄식·최상단은 확정. 구체 위치(응시자 카드 위 배너 / 카드–종합점수 사이 / 종합점수 카드 내)·컴포넌트·`max_chars` 미정. *(제안: 카드–종합점수 사이 강조 스트립, max_chars 90, 2줄 실측 후 확정)*
- **상위%·배수컷 노출**: 소표본 가정값이라 문장 내 수치 단정 지양. 실모집단 산출 정책 확정 시 재검토.
- **액션 출처**: 전적으로 LLM 생성(현재) vs 추후 면접질문 API와 정합. *(제안: 당분간 LLM 생성)*
- **모델·게이트웨이·비용**: 하드스킬 추출 API(`하드스킬/하드스킬-추출-API설계-20260616.md`) 연동 결정과 동일하게.
