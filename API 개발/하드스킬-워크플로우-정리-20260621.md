## 0. 한눈에 — 2단계 워크플로우

```
[1단계] JD → 하드스킬 추출 (+ 지시사항)            (공고당 1회 · 재사용)
   비정형 채용정보 → 표준 JD(8섹션) + required_hard_skills[](3범주·capability)
                    + 하드스킬별 '지시사항'(추출 이유 / 검출 부연)   ※ 키워드 확장 안 함
        ▼
[2단계] 하드스킬 검출 = 근거문장 추출 = 자소서 매칭   (지원자당 N회)
   하드스킬 + 지시사항 → AI(프롬프트)가 자소서에서 근거문장 검출 → 검출/미검출 + 근거문장
        ▼
   결과지 hard_skills.항목[] (확인된/미확인 하드스킬 + 근거문장)
```

> ※ **범위 주의(중요):** 첨부 **연구노트는 1단계(JD 구조화·하드스킬 추출)까지만** 다룬다. **2단계(근거문장 매칭)는 명시적으로 범위 밖**이다 — "하드스킬 평가·점수화는 이 문서 범위 아님", "후속 워크플로우는 연결 가능성만 정의, 실제 작동 방식 미정리"(연구노트 §1-3·§9). → **2단계 원리가 불명확한 근본 이유.**

## 1단계: 하드스킬 추출 (대체로 확정)

출처: 연구노트(주) + 설계초안 `하드스킬-추출-API설계` + 한일시멘트 적용. ✅

### 1-1. 입력 — 고객사 비정형 채용정보 → 필수/선택 분류
- **필수:** `job_title`(누락 시 중단·재요청) · `key_responsibilities`(중단·재요청) · `required_competencies`(진행 가능하나 hard skill 빌 수 있음) · `hiring_purpose`(권장).
- **선택**('미입력' 허용, **임의 추정 금지**): `team` · `collaboration_targets` · `tools` · `industry` · `seniority` · `nice_to_have` · `performance_goals` · `education_level`.

### 1-2. 출력 — 표준 JD 8섹션 + 하드스킬
- 8섹션: `team` / `jd_title` / `application_qualifications` / `job_purpose` / `key_responsibilities` / `performance_kpi` / **`required_hard_skills[]`** / `nice_to_have_requirements` (+ 메타 `ambiguous_missing_information`, `extraction_notes`).
- **`required_hard_skills[]`**: 3범주 분류 + `rewritten_as_capability` + `evidence_from_input`(원문 보존) + `must_have`/`nice_to_have`.
  - **3범주(협의):** `tool_based`(도구·SW) / `method_based`(방법론·절차) / `knowledge_based`(이론·규정·전공). ※ `experience_based`(경험)·`output_based`(산출물)는 **제외**(2026-06-22 협의 축소).
  - `rewritten_as_capability` = 단순 키워드 금지, **목적어 + 동사 + 관찰 가능한 결과물** 한 문장("무엇을 할 수 있어야 하는가").
- **검출 기준(`detection_criteria`, 구 '지시사항' — §1-6 설계):** 하드스킬별로 '자소서에서 이 하드스킬을 검출하는 판정 기준'을 함께 생성 → 2단계 검출의 근거. ※ **키워드 확장은 하지 않는다**(AI 프롬프트 매칭이라 불필요).

### 1-3. AI 판단 규칙 (확정)
- 고객사 입력에 **명시된 내용만** 확정(`evidence_from_input`에 원문 보존). 해석은 `ambiguity_flags`, 구성 불가 항목은 `missing_information`.
- **임의 추가 절대 금지:** 팀명·부서·경력연차·학력·보상·근무지·고용형태.
- Hard ↔ Soft skill 혼동 금지(품질검수 hard fail). 6항목 품질 검수 후 운영 검수.

### 1-4. 한일시멘트 적용 결과 (실제 수행됨)
- 생산직 JD → 하드스킬 **7개**(필수 4 + 우대 3), 각 범주·capability·JD 원문 근거. (SDS r6 참고1) ✅

### 1-5. 담당·산출물
- ✅ **윤방우**가 API·프롬프트 설계 중(작업기준서 §4-2). user 설계초안과 정합. 프로토타입 존재(연구노트 §10 streamlit).
- 출력 3형식: 내부 확인용 JD 문서 / 시스템용 JSON / 엑셀.

### 1-6. '검출 기준'(`detection_criteria`) 설계 — 구 '지시사항' (기획안)
> **명칭 제안:** '지시사항' → **검출 기준**(`detection_criteria`). 기능(자소서에서 보유 여부를 판정하는 기준)을 그대로 드러냄. 기술적으론 '검출 루브릭'(§3 snippetSet에 들어감).
- **역할:** 2단계 AI 검출의 판정 근거 — "자소서에 무엇이 있으면 이 하드스킬을 보유한 것으로 보는가".
- **생성:** 1단계 추출 시 하드스킬마다 함께(JD 근거 기반, 무근거 금지).
- **형식(1~2문장):** ⓐ **인정 조건**(보유로 볼 근거) + ⓑ **배제 조건**(피상적 언급·동음이의 등 인정 안 함).
- **예시**(한일시멘트 '공정 안정화·품질관리'): "공정/실험 변수를 분석·조정해 변동을 줄이거나 품질·재현성을 확보한 경험이 구체적으로 서술되면 검출. '품질이 중요하다'는 인식·다짐만 있으면 미검출."
- **매핑:** 이 검출 기준이 2단계 `COMMON/EXTRACT-EVIDENCE`의 **`rubric`(키별 루브릭)** 으로 그대로 들어간다(§3).

## 2단계: 근거문장 매칭 (원리 미정 — 결정 필요)

> ※ **연구노트 범위 밖**이나, **2026-06-21 user가 매칭 원리를 결정**했다(§2-2). 매칭은 **AI(프롬프트) + 지시사항** 방식이며 **키워드 확장은 미사용**. 아래 §2-1 단편은 결정 이전 기록.

### 2-1. 단편 정보 (출처별)
- (`하드스킬-추출-플로우`) ② **키워드 확장**: 하드스킬 → 동의어·표기변형 `keywords[]`(아카이빙·재사용) → ③ **검출 판단**: 키워드로 찾은 *후보 문장*이 실제 보유 근거인지 AI 판단(동음이의어 대응) → `{status:검출/미검출, evidence_ids, summary, confidence}`. 후보 없으면 AI 호출 없이 미검출.
- (SDS r6) 자소서에서 **[하드스킬 + 확장키워드] 기준 AI 매칭 문장 추출**. "근거문장은 기존 API 활용 가능." 벡터DB 제외.
- (회의 / 송영록) 추출 시 **"지시사항"을 같이 생성** → 그 지시사항으로 자소서 근거문장 추출. **기존 근거문장 API** 활용. **문장 단위로 자른 자소서**를 입력.
- (한일시멘트) hard_skills 검출/근거문장은 **수작업(INTERIM)** — 검증된 자동 방법 아님(작업계획서 §11-2).
- (연구노트 §9) "Hard skill 검증 과제 설계"에 `rewritten_as_capability`가 입력될 수 있다고 **연결 가능성만** 언급(실제 매칭 방식 아님).

### 2-2. ✅ 매칭 방식 결정 (2026-06-21)
- **B 확정:** 1단계에서 만든 **'지시사항'을 근거로, AI(프롬프트)가 자소서에서 하드스킬 근거문장을 검출**한다.
- **A 미사용:** 키워드 확장(동의어·표기변형)은 **하지 않는다** — 매칭을 AI 프롬프트로 하므로 불필요(user).
- 1단계는 하드스킬 **키워드만** 추출 + 하드스킬별 **'지시사항'**(추출 이유 / 검출 부연설명) 생성.
- ※ **용어:** 2단계 = 자소서 매칭 = 근거문장 추출 = 하드스킬 검출 (모두 같은 의미).

### 2-3. 확인·결정 현황
- ✅ **매칭 원리** = AI(프롬프트) + 지시사항 (A 키워드확장 미사용) — 결정(§2-2)
- ✅ **'지시사항' 역할** = JD에서 그 하드스킬로 추출한 이유 / 검출 부연설명 (user)
- ❓ **'지시사항' 정확한 형식·필드명** — 1단계 출력에 어떻게 담을지(신규 요소, 확정 필요)
- ✅ **2단계 구현 = `COMMON/EXTRACT-EVIDENCE`**(키별 근거문장 추출 전용, `rubric`=검출 기준 inline) — **2026-06-22 정식 전환**(§3). 기존 'EVALUATE-CUSTOM-FACTOR 재사용(B)'은 폴백. EXTRACT-EVIDENCE 작성중이라 ❓ 가용성·score 포함은 개발팀 확인
- ❓ **자소서 입력** = 문장 단위 분할(누가?) / ❓ **검출 트리거**(자동 vs 배치) / ❓ `confidence`·신뢰도 노출
- ✅ 후보 키워드 검색 불필요(AI 매칭) / ✅ 벡터DB 미사용 / ※ QC 미구현(재분석 — BP4.1 컨셉)

### 2-4. 담당
- dev팀(윤방우 = 추출/검출). ※ 키워드 확장(장윤경 담당분)은 **폐기**(A갈래). user = 검출 기준 설계 + 송영록 확인 주도.

## 3. 2단계 구현 — 근거문장 API 분석 (B=EVALUATE 재사용 → 갱신: EXTRACT-EVIDENCE 전환)

> **(2026-06-22 갱신·정식 결정)** 신규 참고 `COMMON/EXTRACT-EVIDENCE`(키별 근거문장 추출 전용 API; `rubric`=동적 루브릭, 매뉴얼이 '하드스킬'을 예시로 명시)가 검출에 더 정확히 맞아 **정식 구현으로 전환**. `key`=하드스킬, `rubric`=검출 기준 inline → B안의 '임의 factor키 등록·grade 이진화·N개 묶음' ❓ 해소. EVALUATE 재사용(B)은 폴백. 아래 A/B/C는 그 직전까지의 검토 기록. → `하드스킬검출-API명세서` 참조.

> (검토 기록) 송영록 "기존 근거문장 API 활용 가능"의 정체 = **EVALUATE-CUSTOM-FACTOR**로 판단. factor를 자소서로 평가해 grade + **`reasonSegment`(근거문장)** + 위치(offset)를 반환 → 하드스킬 검출과 구조가 거의 동일.

### 3-1. 구조 매핑
| 하드스킬 검출 | EVALUATE-CUSTOM-FACTOR |
|---|---|
| 검출할 하드스킬 목록 | `factorList[]` |
| **검출 기준**(§1-6) | `snippetSet`(요소별 루브릭) |
| 자소서 | `body`(+`head`) |
| 검출/미검출 | `grade`(`promptGradeOption`로 이진화) |
| 근거문장(+위치) | **`reasonSegment` + `bodyIndex`/offset** |
| 근거문장 개수 제어 | `maxReasonSegment` |

### 3-2. 선택지 (의사결정)
| 안 | 내용 | 평가 |
|---|---|---|
| A. 그대로 | 기존 prompt/snippet 그대로 호출 | ✗ 기존 루브릭이 BP-factor용(high/mid/low/none) → 하드스킬 이진검출에 부적합 |
| **B. 응용(추천)** | EVALUATE 엔진·엔드포인트 재사용 + **하드스킬용 promptName·snippetSet 신규 등록**(snippet=검출 기준), `promptGradeOption`로 검출/미검출 | 검증된 근거문장+위치 엔진 재사용(어려운 핵심 해결), 검출 기준=snippet 직결, ①④의 '공방 프롬프트 재사용' 철학 일치 |
| C. 신규 | 별도 검출 API/프롬프트 신설 | ✗ 근거문장+위치 추출을 새로 구현(낭비) |

→ **추천: B.** 근거문장 추출(어려운 핵심)은 검증된 EVALUATE를 쓰고, 하드스킬용 **프롬프트 + snippet(=검출 기준)** 만 새로 등록.

### 3-3. ❓ B안 확인 (송영록·홍정호)
- JD 유래 하드스킬을 **임의 `factorList` 키 + 신규 `snippetSet`** 으로 등록 가능한가
- `grade`를 **검출/미검출 이진**으로 둘 수 있나(`promptGradeOption`=`["high","none"]` 등)
- 한 호출에 하드스킬 **N개 묶어** 처리 가능한가(개수·토큰 한도)
