## 0. 작업 개요

### 최종 목표
- 아래 **4개 API**에 대해 **① 워크플로우 + ② API 명세서 + ③ 공방 등록용 프롬프트**를 작성한다.
- 도달선: 개발자가 별도 설계 없이 **바로 구현 착수**할 수 있는 수준("개발 직전")까지.
- 본 문서가 그 작업의 **기준·히스토리 문서**다. 결정·변경은 §9 변경 히스토리(CH-xxx)에 누적한다. (추후 개발팀 공유 가능성 있음)

### 대상 API 4종
| # | API | 구분 | 경유 |
|---|---|---|---|
| 1 | 한 줄 코멘트 생성 | 신규 | 공통 execute API |

### 비개발자 역할 범위 (확정 전제)
- **하는 일(1층):** 워크플로우 정의, 입출력 스키마, 프롬프트 설계, 품질 게이트, API 명세서.
- **개발팀 몫(2층):** 실제 시스템 연동, 모델·비용 운영, 저장소, 동기/비동기, 보안·개인정보. → 회사 **공통 execute API**가 LLM 호출 게이트웨이를 제공하므로 1층 집중이 가능해짐(§2).
- ※ 채용 개인정보(개인정보보호법·채용절차법) 민감 → 비개발자 산출물이 직접 운영 엔드포인트가 되지 않는다. 명세·프롬프트를 제공하고 운영화는 개발팀이 한다.

## 1. 핵심 전제 — 공통 execute API 경유 (2026-06 회의)

- 회사에 **공통 프롬프트 실행 API(COMMON/PROMPT-EXECUTE)**가 있다. 몬스터에서 사용 중, **프리즘에도 활성화 예정**(임수경).
- 개발6 유닛 리소스 부족(AXP 일정, 신규 프로젝트 **7월 중순** 실투입) → execute API로 **디펜던시 우회**, **다음주 초 테스트 버전** 제공 가능.
- 의미: 우리는 **프롬프트 + 입출력 계약 + 워크플로우**만 정확히 정의하면 된다. 이것이 "개발 직전까지" 도달을 가능케 하는 핵심 경로.
- 단, 하드스킬(추출/매칭)은 송영록이 **전용 초안**을 1~2일 내 제공(입출력 명세·문장 개수 제어 포함) 후 장윤경·윤방우가 이어받는 구조.

## 1-1. execute API 동작 요약 & 사용 조건 (매뉴얼 r8 반영)

- **공방 = 저장, execute API = 실행.** 공방(prompt.muhayu.com)에는 프롬프트 본문(`{{ }}` 입력변수)과 출력 JSON Schema를 *저장*만 한다. execute API가 요청 시 공방에서 프롬프트를 꺼내 변수(`keyValue`)를 채우고 **LLM을 호출**해 schema대로 검증된 결과를 반환한다. → **프롬프트만 공방에 올려선 아무것도 실행되지 않는다**(러너 필요).
- **요청 핵심:** `workspaceName`+`promptName`(조합이 유니크) · `llmServiceKey`(JARVIS LLM 서비스키) · `keyValue`(변수 dict) · `config.onMissingVariables`(error/emptyString) · `config.llmTimeoutSec`(기본 60).
- **응답:** `status`(ok/fail) · `result`(공방 output JSON Schema가 **Strict Mode**로 강제되는 영역) · `extraInfo`(모델·토큰·prompt_version).
- **사용 가능 조건 — 둘 다 만족할 때만(매뉴얼 명시):** ① LLM 응답을 **후처리 없이 그대로** 사용 ② 출력 schema가 **고정**(동적 변동 없음).
- **이득:** LLM 호출·키 관리·모델 라우팅·**출력 스키마 강제**·버전·토큰 집계를 API가 대행 → 자체 LLM 호출기 개발(=개발6 의존) 불필요. 비개발자 작업이 "프롬프트 + 입출력 정의"로 축소.

### API별 execute 적합성 판단 (2026-06-21)
| API | 적합성 | 근거 |
|---|---|---|
| ① 한 줄 코멘트 | ✅ 사용 | 단발 호출·고정 스키마. 품질게이트는 프롬프트 내 자가검증으로, 재시도 필요 시 얇은 래퍼만 추후 |
| ② 하드스킬 추출 | ✅ 사용 | JD→하드스킬+지시사항, 단발 호출·고정 스키마 |
| ③ 하드스킬 매칭 | ※ 단독 불가 | 후보검색→스킬별 AI 판단→**기존 근거문장 API 재사용**→집계의 **다단계 파이프라인**. execute는 부품, 오케스트레이션은 개발팀(송영록 전용 구현) |
| ④ 자소서 특장점 | ✅ 사용 | 자소서 본문 1개→특장점 4~5개, 단발 호출. 공방 프롬프트 수정이 사실상 전부 |

## 3. 용어

| 용어 | 의미 |
|---|---|
| **execute API** | 공통 프롬프트 실행 API (COMMON/PROMPT-EXECUTE). LLM 호출 게이트웨이 |
| **공방** | 사내 운영 **프롬프트 저장소**. 프롬프트를 저장해 두면 API(execute 등)가 런타임에 이 프롬프트를 가져와 실행한다 |

## 4. API별 작업 기준 & 현황

### 4-1. 한 줄 코멘트 생성 (신규) — SDS r1 반영
- **목표:** BP 평가결과 → 한 문장(강점→단점→액션, 두괄식). 결과지 **P1 최상단**.
- **경유:** 공통 execute API(§1-1) — 공방 프롬프트 + 출력 JSON Schema.
- **입력(확정 방향):** **강점 2 + 검토 2 = 총 4개 factor**(SDS 플로우)를 받아 생성. 출처 = **EVALUATE-CUSTOM-FACTOR**(factor별 `grade`·`explain`·`reasonSegment`·`score`) + BP 점수 산출 API(metric 점수·평균). 강점/검토 **선별은 업스트림**(기준 문서: "BP평가 콘텐츠 개선안") → 본 API는 선별된 4개를 받아 *합성*만.
- **출력:** `one_liner` + `parts`(strength/weakness/action) + `tone`(recommend/review) + `meta`(grounded).
- **담당/상태:** 최고운 인풋 정의 → 송영록(execute). **작업 착수 2026-06-21** → 산출물 `한줄코멘트-API명세서-20260621.md`.
- **오픈이슈:** ① digest 범위(4 factor + 6 metric 평균 동반?) ② `max_chars`(제안 90)·char_count ③ 소표본 상위%·배수컷 수치 단정 금지 ④ 공방 workspace/promptName/serviceKey 명명.

### 4-2. 하드스킬 추출 (신규) — SDS r6 반영
- **목표:** JD → **하드스킬 키워드 5~7개 추출**(3범주[협의: 도구·방법론·지식]·capability·근거) **+ 하드스킬별 '지시사항' 생성**(추출 이유/검출 부연 → 2단계 검출 근거). ※ **키워드 확장 안 함**(2026-06-21). 공고당 1회·아카이빙 재사용.
- **담당:** **윤방우(API·프롬프트 설계 중)** + 매니저 화면 CRUD 관리. 프롬프트 초안은 user 설계(`하드스킬-추출-API설계`)와 정합.
- **입력:** JD(PDF/HWP/DOCX → 텍스트). **출력:** `required_hard_skills[]` + `missing_information` + `ambiguity_flags` + `extraction_notes`.
- **상태:** **dev팀 주도**(user는 설계 입력 제공). JD 업로드 접수 화면은 별도 SDS r7.
- **오픈이슈:** ① JD→텍스트 변환 자동/수동 ② 파일형태·개수 제한 ③ 하드스킬 개수 **5~7개 확정**(2026-06-22) ④ 실행 방식(전용 API vs execute+공방, 윤방우).
- **산출물:** `하드스킬추출-API명세서-20260622.md`. **검출 기준(`detection_criteria`) 출력 포함** 확정(2026-06-22).

### 4-3. 하드스킬 검출(=근거문장 추출=자소서 매칭) (신규) — 2026-06-21 결정 반영
- **목표:** 자소서에서 하드스킬 **검출/미검출 + 근거문장**(결과지 최상단 행). ※ 검출=근거문장 추출=매칭 동의어.
- **워크플로우(결정):** 1단계 하드스킬 **키워드 + 지시사항** → **AI(프롬프트)가 자소서에서 근거문장 검출**. **키워드 확장 미사용**(AI 매칭이라 불필요). 벡터DB 제외.
- **담당/상태:** dev팀(윤방우·장윤경). QC 미구현(재분석 — BP4.1 컨셉).
- **오픈이슈:** ① 검출 기준(`detection_criteria`) 채택됨(인정+배제) ② 2단계 구현 = **`COMMON/EXTRACT-EVIDENCE`**(key=하드스킬·rubric=검출 기준 inline), EVALUATE 응용(B)은 폴백 ③ **API 2개**(추출 신규 + 검출=EXTRACT-EVIDENCE) ④ 잔여 ❓: 가용성(작성중)·score 포함·판정 임계값·트리거. → 정리 `하드스킬-워크플로우-정리-20260621.md`(§3).
- **산출물:** `하드스킬검출-API명세서-20260622.md`(`COMMON/EXTRACT-EVIDENCE` 기반: key=하드스킬·rubric=검출 기준 inline·evidence=근거문장). EVALUATE는 폴백. 잔여 ❓(가용성·score 포함·판정 임계값)는 명세서 §0.

### 4-4. 자소서 특장점 요약 (기존 PAC 수정) — CUSTOM-SUMMARY r20 반영
- **목표:** 자소서 **핵심 내용 4~5개 중립 요약**(※ 가치판단·장단점 평가 아님 — 단순 요약). 각 항목 **짧은 명사구 ~20자**(실측 평균 22자).
- **원천:** CUSTOM-SUMMARY의 요약 기능(신디 관리기/Django admin 프롬프트 관리). ※ '장단요약'이 아니라 일반 내용 요약.
- **방식(임수경):** 해당 프롬프트를 **공방 이관 후 4~5개로 수정** → **execute API로 새 API화**(기존 PAC 모듈 동반 불필요). **입력 = 자소서 본문(body)만**(`config.unit=whole` 계열).
- **오픈이슈:** ① 기존 특장점 프롬프트 원문 수령(임수경) ② 4~5개 출력 스키마·문장수 제어 ③ 결과지 `summary-bullets`(4~5개) 정합 — `작업계획서.md` CH-024.

## 5. 공통 작업 기준
- **프롬프트 자산화(공방):** 각 API 프롬프트는 코드에 박지 않고 **공방(프롬프트 저장소)에 저장** → API가 런타임에 가져와 실행. 따라서 **'공방 등록용 프롬프트'가 API별 핵심 산출물**이며, 코드 수정 없이 프롬프트만 갱신해 반복 개선한다(예: API④는 기존 PAC 프롬프트를 공방으로 옮겨 4~5문장으로 수정).
- **무근거 금지:** 입력에 있는 내용만. 환각 금지. 근거(원문/근거문장) 보존.
- **법령 표현:** 합격/불합격/적격/부적격/탈락 직접 표기 금지 → 권장/검토 필요/확인 (AI기본법, SDS r25).
- **품질 게이트:** 각 API 출력은 자동 검증(필수 요소 포함·금지어·grounded·길이) 후 통과. (설계 초안의 게이트 계승)
- **I/O 계약:** 모든 API는 명세서에 요청/응답 JSON 스키마 + 상태코드 + 게이트를 명시. execute API 입력 규격에 맞춰 정규화.
- **출력 형식 재사용:** 결과지 렌더 구조(`data/bp_evaluation_data.json`, `template-bp42.html`)를 출력 타깃으로 본다.
- **API 명세서 양식:** 사내 표준(`EVALUATE-CUSTOM-FACTOR` 매뉴얼 구조)을 따른다 — `1.개요 / 2.Service URL / 3.Function Specifications(Request·Response 파라미터 표) / 4.Examples / 5~.참고`. 파라미터 표 컬럼: `이름·type·depth·default(허용여부)·memo·example`.
