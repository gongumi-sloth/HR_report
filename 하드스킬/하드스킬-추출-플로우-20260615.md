# 하드스킬 추출 — 흐름 · 결정 · 개발 계약

> '직무지식'에 하드스킬을 추가해, 자소서에서 **확인된 / 확인되지 않은 하드스킬**로 구분해 보여줍니다.
> 프리즘 BP · 2026-06-15 · 개발 / 연구개발 미팅용

---

## 전체 흐름

```text
① 채용공고 준비  (공고당 1회 · 재사용 가능)
   1. 접수(고객사)  →  2. 추출(AI→운영검수)  →  3. 확장(AI→운영검수→아카이빙)
                                                      │
                                                      ▼
② 지원자 평가  (지원자당 N회)
   4. 검출 판단(시스템+AI)  →  5. 결과 표시(결과지)
```

### ① 채용공고 준비 — 공고당 1회 · 재사용 가능
1. **접수** *(고객사)* — JD(직무기술서) 파일을 **필수**로 업로드한다.
2. **하드스킬 추출** *(AI → 운영 검수)* — AI가 JD에서 하드스킬 키워드·근거를 뽑고, **운영이 검수·수정**한다.
3. **키워드 확장** *(AI → 운영 검수 → 아카이빙)* — AI가 동의어·유사 표현으로 넓히고 운영이 검수. **고객사·채용별로 저장해 재사용**한다.

### ② 지원자 평가 — 지원자당 N회
4. **검출 판단** *(시스템 + AI)* — 키워드로 자소서 후보 문장을 찾고, **AI가 실제 보유 여부를 판단**한다(동음이의어 대응). 항목별 **검출 / 미검출** 확정.
5. **결과 표시** *(결과지)* — **확인된 하드스킬 / 확인되지 않은 하드스킬**을 근거 문장과 함께 보여준다.

---

## 확정된 결정

- **결정 1 · 검수** — 추출·확장 결과는 **운영(어드민)이 검수**한다 (당분간).
- **결정 2 · 확장/재사용** — 공고마다 생성하되(고객사·채용별로 다름) **아카이빙해 재사용**. 고객사가 이전 공고 JD 적용을 요청하면 운영이 불러와 적용할 수 있어야 한다.
- **결정 3·4 · 검출 방식** — **AI로 검출 여부 판단**(동음이의어 등 대응). **벡터DB는 이번 범위 외.** 신뢰도는 내부 판정용(결과지 노출 여부는 추후).
- **결정 5 · 접수** — JD 업로드는 **필수**, **파일 형태**로 받는다.

## 단계별 데이터 계약

| 단계 | 입력 | 출력 |
|---|---|---|
| **1 접수** | JD 파일 | `jd_text`(추출 본문) + 메타 `{고객사ID, 채용공고ID}` |
| **2 추출** (프롬프트①) | `jd_text` | `[{ name, jd_evidence }]` → 운영 검수 후 확정 |
| **3 확장** (프롬프트②) | 확정된 `name` 목록 | `[{ name, keywords[] }]` → 검수 후 **프로파일로 저장(재사용)** |
| **4 검출** (프롬프트③) | 키워드 후보 검색 결과 `{ skill, candidate_sentences[] }` | `{ name, status:검출\|미검출, evidence_ids[], summary, confidence }` |
| **5 결과** | 4의 출력 배열 | `hard_skills.항목[]` → 결과지 렌더 (기존 구조 그대로) |

## 프롬프트 계약 (3개)

### 프롬프트 ① — 하드스킬 추출
JD 본문에서 하드스킬과 JD 내 근거 문구를 추출. **공고당 1회.**

**입력**
```json
{ "jd_text": "<채용공고/JD 전문>" }
```
**출력**
```json
{
  "hard_skills": [
    { "name": "Excel", "jd_evidence": "영업 실적 데이터 분석 및 리포트 작성" },
    { "name": "Salesforce Sales Cloud Consultant", "jd_evidence": "CRM 기반 고객 관리" }
  ]
}
```

### 프롬프트 ② — 키워드 확장
검수된 하드스킬을 자소서 검색용 동의어·표기변형으로 확장. **공고당 1회 + 아카이빙.**

**입력**
```json
{
  "job_context": "영업관리",
  "skills": ["Excel", "Salesforce Sales Cloud Consultant"]
}
```
**출력**
```json
{
  "expanded": [
    { "name": "Excel",
      "keywords": ["Excel", "엑셀", "스프레드시트", "피벗테이블", "VLOOKUP"] },
    { "name": "Salesforce Sales Cloud Consultant",
      "keywords": ["Salesforce", "세일즈포스", "SFDC", "CRM"] }
  ]
}
```

### 프롬프트 ③ — 검출 판단 *(핵심)*
키워드로 찾은 **후보 문장**이 실제로 그 하드스킬 보유 근거인지 AI가 판단(동음이의어 대응). **지원자 × 스킬마다.**

**입력**
```json
{
  "skill": { "name": "Excel", "keywords": ["Excel", "엑셀", "피벗테이블"] },
  "candidate_sentences": [
    { "id": 16, "text": "Excel을 활용한 영업 실적 분석·피벗 테이블 작성으로…" }
  ]
}
```
**출력**
```json
{
  "name": "Excel",
  "status": "검출",
  "evidence_ids": [16],
  "summary": "Excel 피벗 테이블 활용 실적 분석·리포트 경험 확인.",
  "confidence": 0.92
}
```
> `status`는 `검출 | 미검출`, `confidence`는 내부 판정용.
> ※ 후보 문장이 **없으면 AI 호출 없이** `status:"미검출"` (비용 절감).

## 미팅에서 확정할 연동 항목
> 백엔드 구조라 별도 결정 필요. 아래 6가지가 이번 미팅의 실제 안건.

- **접수 파일** — JD 파일 저장 위치·파서(문서→텍스트) 연동 방식
- **LLM 호출** — 사용 모델, 토큰·비용 한도, 호출 게이트웨이
- **자소서 데이터 소스** — 어디서 문장 단위로 가져오나 (기존 `essay_sections` / `evidence_sentences` 구조에 매핑)
- **프로파일 저장소** — 확장 결과의 아카이빙·버전·재사용 조회 (고객사·채용 키)
- **검출 트리거 시점** — 지원자 접수 시 자동 실행 vs 배치 처리
- **후보 검색 수준** — 키워드 단순 일치 / 형태소·표기 정규화 어디까지

## 지금 이걸로 개발 시작 가능한가

**프롬프트 ①②③과 단계별 데이터 계약은 정의됐으므로, 프롬프트 설계와 처리 로직은 바로 착수 가능**합니다.
다만 위 **'연동 항목' 6가지**(저장소·데이터 소스·트리거 등)는 귀사 백엔드 구조에 달려 있어, 이번 미팅에서 확정해야 전체 개발이 막힘없이 진행됩니다.
